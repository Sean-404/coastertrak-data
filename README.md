# coastertrak-data

Data ingestion, processing, validation, and quality-control pipeline for [CoasterTrak](https://github.com/coastertrak/CoasterTrak).

This is a **standalone repository**. It does not modify the CoasterTrak website or its production database. Its purpose is to produce a clean, reliable, reproducible dataset that CoasterTrak can eventually consume.

## Philosophy

Do **not** scrape Wikidata and copy it directly into CoasterTrak. Instead:

```
Wikidata / external sources
        ↓
   Raw source data (immutable)
        ↓
   Normalisation
        ↓
   Entity matching
        ↓
   Validation
        ↓
   Conflict detection
        ↓
   Data quality scoring
        ↓
   Human review
        ↓
   Canonical CoasterTrak dataset
        ↓
   Export for CoasterTrak
```

The pipeline is **reproducible** and **deterministic**. Raw data is never overwritten by processing logic.

## Architecture

```
coastertrak-data/
├── data/
│   ├── raw/          # Immutable source snapshots (gitignored)
│   ├── processed/    # Mapped canonical entities per run
│   ├── review/       # Human review queue (generated by validate)
│   ├── overrides/    # Manual corrections (survive re-imports)
│   ├── reports/      # Validation reports per run
│   └── output/       # Final canonical export
├── fixtures/         # Committed test data
└── src/
    ├── canonical/    # Zod schemas + TypeScript types
    ├── sources/      # Source adapters (Wikidata first)
    ├── normalize/    # Name, date, status, coordinate normalisation
    ├── validate/     # Quality rules and reporting
    ├── matching/     # Duplicate detection
    ├── pipeline/     # process, validate, export orchestration
    ├── confidence/   # Quality scoring
    ├── overrides/    # Override schemas
    └── export/       # CoasterTrak export mapping
```

### Layers

| Layer | Responsibility |
|-------|----------------|
| **Sources** | Fetch raw data from external APIs; preserve source IDs and raw responses |
| **Raw storage** | Immutable dated snapshots; reprocessable without re-fetching |
| **Processing** | Map, normalise, match entities, validate, score quality |
| **Review** | Surface ambiguous records for human decisions |
| **Overrides** | Apply manual corrections without touching raw data |
| **Export** | Produce deterministic canonical JSON for CoasterTrak import |

## Data flow

1. **Ingest** — Source adapter fetches data and writes paginated raw JSON to `data/raw/{source}/{runId}/`.
2. **Process** — Raw bindings are mapped to canonical entities with provenance; overrides from `data/overrides/` are applied.
3. **Validate** — Rules produce errors, warnings, review queue files, and a markdown report.
4. **Export** — Canonical dataset written to `data/output/` plus `coastertrak-export.json` for future DB import.

Raw data is **never modified**. Changing processing logic six months from now should allow reprocessing old raw snapshots without querying Wikidata again.

## Source strategy

Wikidata is the first source. The `SourceAdapter` interface in `src/sources/types.ts` allows adding future sources (`official/`, `rcdb/`, etc.) without changing core pipeline logic.

Wikidata-specific code lives only in `src/sources/wikidata/`:

- `client.ts` — HTTP SPARQL client with retry and rate limiting
- `queries.ts` — Separate SPARQL queries for **coasters** and **parks**
- `ingest.ts` — Paginated raw save
- `mapper.ts` — Raw SPARQL bindings → canonical parks/coasters with provenance

## Canonical schema

The canonical model represents what CoasterTrak **needs**, not Wikidata's shape. See `src/canonical/`.

### Provenance

Every important field is wrapped in `SourcedValue<T>`:

```json
{
  "height": {
    "value": { "value": 77, "unit": "m" },
    "provenance": [
      {
        "source": "wikidata",
        "sourceId": "Q123456",
        "retrievedAt": "2026-08-28T00:00:00.000Z"
      }
    ],
    "confidence": "HIGH"
  }
}
```

This answers: *"Why does CoasterTrak think this coaster is 77 metres tall?"*

### Country

Internal storage uses **ISO 3166-1 alpha-2** codes (`"SG"`, `"US"`, `"DK"`). Display labels (e.g. `"Singapore"`) are derived at export time via `src/canonical/country.ts`.

### Status

| Canonical | Meaning |
|-----------|---------|
| `OPERATING` | Currently operating |
| `UNDER_CONSTRUCTION` | Not yet open |
| `TEMPORARILY_CLOSED` | Expected to reopen |
| `CLOSED` | Permanently closed |
| `REMOVED` | Demolished / removed (preserved for history) |
| `UNKNOWN` | Insufficient data |

Historical coasters remain in the dataset with appropriate status — they are not deleted.

### Units

Metric internally (`m`, `m/s`, `s`). Imperial conversion happens at export for CoasterTrak compatibility.

## Validation strategy

Validation produces three severity levels:

- **ERROR** — Must fix before trusting export (e.g. missing park, invalid Wikidata ID)
- **WARNING** — Suspicious but potentially legitimate (e.g. outlier stats, country conflict)
- **INFO** — Informational (e.g. low-confidence duplicate candidates)

Documented stat limits (flagged, not deleted):

| Field | Limit |
|-------|-------|
| Height | 160 m |
| Speed | 70 m/s |
| Length | 3000 m |
| Inversions | 14 |
| Coaster–park distance | 50 km |

Run `npm run validate` or `npm run report` to generate:

- `data/reports/wikidata/{runId}/report.json` and `report.md`
- `data/review/duplicate-parks.json`, `duplicate-coasters.json`, `country-conflicts.json`, `suspicious-values.json`, `missing-data.json`

## Entity matching strategy

Park and coaster duplicate detection uses multiple signals:

- Source ID match (exact duplicates → error)
- Normalised name similarity (Dice coefficient)
- Aliases
- Coordinates + country proximity
- Manufacturer / opening date (coasters)

Ambiguous matches are written to the review queue with `action: "REVIEW"` — **never auto-merged**.

## Manual overrides

Overrides are applied during **process**, after mapping, from `data/overrides/parks.json` and `coasters.json`. Example templates are committed as `*.example.json`.

## Output format

```
data/output/
├── meta.json
├── parks.json
├── coasters.json
└── coastertrak-export.json   # Legacy DB-shaped export for future import
```

Output is deterministic for a given raw run + override set.

## Running the pipeline

### Setup

```bash
cd coastertrak-data
npm install
cp .env.example .env   # optional: set WIKIDATA_USER_AGENT for live ingest
```

### Commands

| Command | Description |
|---------|-------------|
| `npm run ingest` | Copy fixtures → `data/raw/` (default) |
| `npm run ingest -- --live` | Query Wikidata live (use `--max-rows` for safety) |
| `npm run process` | Map raw → canonical, apply overrides → `data/processed/` |
| `npm run validate` | Validate processed catalog, write reports + review queue |
| `npm run validate -- --fixtures` | Validate committed fixture JSON only |
| `npm run report` | Print quality report to stdout |
| `npm run export` | Export to `data/output/` |
| `npm run pipeline` | Full run: ingest → process → validate → export |
| `npm test` | Run Vitest unit tests |
| `npm run typecheck` | TypeScript check |
| `npm run lint` | ESLint |

## CoasterTrak integration (future)

The export adapter in `src/export/coastertrak.ts` documents how canonical data maps to the CoasterTrak Supabase schema:

| Canonical | CoasterTrak DB |
|-----------|----------------|
| `countryCode` → display lookup | `parks.country` |
| `coordinates` | `parks.latitude`, `parks.longitude` |
| `sourceIds.wikidata` | `parks.external_id`, `coasters.wikidata_id` |
| `height` (m → ft) | `coasters.height_ft` |
| `speed` (m/s → mph) | `coasters.speed_mph` |
| `status` (mapped) | `coasters.status` |

Import will be a separate script in CoasterTrak that reads `data/output/` — **not implemented yet**.

### Relationship to in-repo pipeline

CoasterTrak currently has a partial pipeline in `src/lib/coastertrak-data/`. That code will eventually be retired in favour of consuming this repository's output. This repo is the long-term home for data quality work.

## Design principles

1. Raw data is immutable
2. Processing is deterministic
3. Production CoasterTrak is never modified directly
4. Ambiguous entities are flagged, not silently merged
5. Manual overrides are separate from source data
6. Every important value has provenance
7. Validation catches errors without destroying unusual records
8. Architecture supports additional sources
9. Keep it simple
10. Correctness over quantity

## Testing

Tests use committed fixtures in `fixtures/` — never production data as mutable fixtures.

```bash
npm test
```

Edge cases covered in fixtures:

- Fårup Sommerland / Fårup Sommarland (duplicate candidate)
- Universal Studios Singapore / Malaysia country conflict
- Historical removed coaster (Son of Beast)
- Missing park linkage
- Suspicious outlier stats (Hyperion)
